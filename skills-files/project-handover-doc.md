# 專案交接說明文件產生器

## 這個技能在做什麼

在一個多步驟任務（特別是 Claude Code 跑完一長串動作）結束後，把「剛剛到底做了什麼、為什麼這樣做、之後怎麼接手」完整寫成一份文件，交給一個不懂技術的人也能看懂、照著用、照著維護。

對象預設是 Tarshar（小D）本人，她自述在自己的製造／系統領域之外屬於非技術背景，所以這份文件的讀者就是一個「聰明但不懂行話的小白」。

## 觸發後的第一步：先盤點真實發生過的事

不要憑空想像。動筆前先回顧這次對話／這段工作真正發生過什麼：

- 使用者最初交付的任務是什麼
- 實際執行了哪些步驟、用了哪些工具或指令
- 過程中做了哪些關鍵決定、使用者有沒有中途修正方向
- 最後產出了哪些檔案、放在哪裡

如果有任何一段你其實沒有把握（例如某個檔案的用途不確定），就在文件裡誠實標註「這一段建議再確認」，不要為了讓文件好看而填入沒發生過的內容。誠實優先於漂亮，這是硬規則。

## 輸出格式：固定六段結構

依序產出以下六段，標題就用這六個。每一段都用白話寫，遇到專業名詞就順手在後面加一句口語解釋。

### 1. 這次的目標
一兩句話講清楚：使用者原本要的是什麼，最後完成了什麼。讓讀者三秒內知道這份文件在講哪件事。

### 2. 我做了哪些事
按時間順序條列每個主要步驟，一步一行。動詞開頭，講人話，例如「先把舊資料備份起來」「再建立一個新的設定檔」。不要貼一大段程式碼，必要時只放關鍵那一行並說明它在做什麼。

### 3. 為什麼這樣做
針對第 2 段裡的關鍵決定，解釋背後的原因。重點是讓讀者懂「為什麼不選別的做法」。這一段是這份文件最有價值的地方，因為步驟可以重看，但當時的判斷邏輯最容易遺失。

### 4. 檔案在哪、各是什麼用途
條列這次產出或改動的檔案清單，每個檔案寫上：位置、名字、一句話用途。讓讀者知道哪個檔案該動、哪個別碰。

### 5. 之後我可以怎麼用
站在使用者的日常立場寫：平常要怎麼操作、想改東西時從哪裡下手、要重跑一次的話該做什麼。用「你只要…」「如果你想…就…」這種第二人稱口吻。

### 6. 注意事項與常見問題
列出容易踩雷的地方、不要亂動的檔案、可能會出錯的狀況與對應方式。寧可多提醒，也不要讓小白事後踩坑。

## 語氣與風格規則

- 全程台灣習慣的繁體中文。
- 讀者是小白，所有專業名詞都要附一句白話解釋，例如「環境變數（就是給程式看的設定值，像是一張小抄）」。
- 不要用破折號。
- 陪跑夥伴的口吻：像一個懂的人坐在旁邊，不疾不徐地帶著你看懂，不是冷冰冰的技術文件。
- 不誇大、不杜撰，只寫真實做過的事。

## 產出與存檔

- 在 Claude Code 環境：把文件存成 Markdown 檔放在專案根目錄，檔名格式 `交接說明_[專案或任務名]_[YYYYMMDD].md`，存完告訴使用者檔案位置。
- 在 Claude 聊天視窗環境：直接把完整文件輸出在對話中；如果使用者要檔案，再存成 `.md` 並提供下載。

## 收尾自我檢查

產出前快速核對：
1. 六段都在嗎？
2. 每個專業名詞都有白話解釋嗎？
3. 內容全部是真實發生過的事嗎，有沒有不小心腦補？
4. 一個不懂技術的人讀完，能不能自己接手？

四項都過了再交出去。
